# 目標

審查 `$ARGUMENTS` 指定範圍；未指定時審查整個 repository。

逐條檢視所有 Claude 專案指令，直接完成必要的刪除、精簡、改寫及搬移。

只修改下列內容，不修改產品程式碼：

* `CLAUDE.md`
* `.claude/CLAUDE.md`
* 子目錄中的 `CLAUDE.md`
* `.claude/rules/**/*.md`
* 必要時新增或調整 `.claude/skills/*/SKILL.md`

不要修改 `CLAUDE.local.md`，除非使用者明確指定。

# 審查範圍

先找出並閱讀：

1. 所有 `CLAUDE.md`
2. `.claude/rules/**/*.md`
3. `CLAUDE.md` 使用 `@` 引入的檔案
4. 相關 `SKILL.md`，用來檢查重複流程
5. 支援或反駁現有規則的程式碼、設定、測試及文件
6. 若存在 `AGENTS.md`（或其他 agent 的指令檔），一併閱讀但**不修改**：只用來偵測與 `CLAUDE.md` 重複或矛盾的規則

`AGENTS.md` 等非 Claude 指令檔不在本 skill 的修改範圍。發現內容與 `CLAUDE.md` 衝突時，列入最終回報的「發現的衝突」，由使用者決定如何處理。

必須檢視每一個段落與 bullet，不得只檢查標題。

將同一 bullet 中的多項要求拆成個別原子規則後判斷。

# 每條規則的判斷方式

依序回答：

1. 這條規則是否適用於此作用範圍內的大部分工作？
2. 幾個月後是否仍可能成立？
3. Claude 是否能從目前程式碼、設定、測試或權威文件中快速且無歧義地找到？
4. 即使可以找到，重新探索是否成本高、容易誤判或出錯代價高？
5. 規則是否具體、可執行、可驗證？
6. 是否與其他指令重複、衝突或描述不同版本的事實？
7. 它屬於長期事實、局部規則、操作流程、參考資料，還是強制限制？

「程式碼中找得到」不是唯一刪除條件。

若資訊藏得深、存在多種看似合理的做法、涉及重要不變式，或錯誤選擇會造成重大問題，應保留精簡後的規則。

符合下列任一條件，且已用 Glob/Grep 搜尋仍無法判斷資訊是否可自行找到時，最多使用一個 Explore 子代理進行獨立搜尋：審查範圍內有 5 份以上 `CLAUDE.md` 與 rules 檔案，或該規則牽涉的程式碼分散在 3 個以上頂層目錄。

不符合上述條件時，直接用 Glob/Grep/Read 自行查證。不要使用子代理重複驗證已完成的分析。

# 處置類型

每條規則只能選擇一個主要處置。

## KEEP_ROOT

保留在根目錄 `CLAUDE.md`：

* 幾乎所有工作都會用到
* 長期穩定
* 專案特有
* 不容易快速推導
* 錯誤會影響整個系統

## MOVE_PATH

只適用特定目錄或模組：

* 目錄級背景與不變式放至該目錄的 `CLAUDE.md`
* 檔案類型或 glob 規則放至 `.claude/rules/*.md`，並設定 `paths`

例如，僅適用 Web 的規則不得留在根目錄。

## MOVE_SKILL

以下內容移至 `.claude/skills/<name>/SKILL.md`：

* 多步驟操作流程
* 定期維護工作
* Checklist
* Deployment、migration、release 或 audit 流程
* 只有特定任務才需要的詳細指令

預設將具有副作用或成本較高的流程設定為：

```yaml
disable-model-invocation: true
```

## MOVE_DOC

詳細背景、設計說明、歷史紀錄或長篇參考資料移至正式文件。

`CLAUDE.md` 只保留：

* 何時需要查閱
* 權威文件路徑
* 不可忽略的結論

不要使用 `@file` import 來假裝縮短內容；被 import 的檔案仍會進入啟動 context。只有每次工作都必須完整載入時才使用 import。

## REWRITE

保留概念但重新撰寫：

* 語意模糊
* 無法驗證
* 混合多項要求
* 使用暫時性的實作細節描述長期規則
* 缺少適用範圍或例外條件

## DELETE

刪除：

* Claude 已具備的一般程式設計常識
* 可從標準設定快速且唯一推導的資訊
* 完整目錄樹、套件清單或依賴版本快照
* 當前測試數量、migration 數量、短期進度或日期
* 已失效的實作狀態
* 歷史敘述
* 重複規則
* 沒有具體行為要求的產品介紹
* 「寫好程式」、「注意品質」、「記得測試」等空泛要求
* 已由更精確規則完整涵蓋的內容

「已失效的實作狀態」與「歷史敘述」只在純粹記錄過去、不含行為要求時才刪除。若敘述中帶有「因為踩過某個坑所以不這樣做」這類仍然有效的約束，改用 REWRITE 保留該約束並刪去敘事；無法由 repository 證實時保留精簡版本並列入「待人工確認」。判斷不確定時一律保留，不刪除。

## ENFORCEMENT_GAP

規則要求「絕對禁止」、「一定不能」或涉及安全、資料損失與正式環境風險，但目前只寫在 `CLAUDE.md` 時：

* 保留必要的簡短行為規則
* 標記為 enforcement gap
* 指出適合的 Hook、CI、測試、permission 或 linter
* 本次不得自行擴大範圍實作 enforcement，除非使用者明確要求

# 應主動補充的內容

只有 repository 中有明確證據時才新增，不得猜測。

優先尋找：

1. 不能違反的架構或資料不變式
2. 專案特有且固定的處理流程
3. 修改某項內容時必須同步修改的檔案、schema、測試或文件
4. 各類工作的實際完成條件
5. 不知道某件事時應查閱的 source of truth
6. 容易反覆踩到、且無法快速從表面程式碼看出的陷阱
7. 非標準的 build、test、migration 或 deployment 指令

不要加入：

* 尚未定案的規劃
* 根據推測產生的規則
* 可以直接從 package scripts 看出的標準命令
* 通用最佳實踐
* 泛用的「重新檢查」或「再次驗證」要求

完成條件應寫成具體命令或可觀察結果，而不是籠統要求。

# 編寫要求

* 使用簡短、直接、可執行的句子
* 一個 bullet 只表達一項規則
* 先寫行為，再寫必要理由
* 保留專案既有術語
* 路徑、命令及識別字使用反引號
* 避免重複 README、架構文件與產品文件
* 不保留「目前」、「現在」、「近期」等容易過期的描述
* 根目錄及每份 nested `CLAUDE.md` 各自目標控制在 200 行內
* 行數以「該檔案被載入時實際進入 context 的內容」計算：自身內容加上它 `@import` 的檔案。搬進 import 檔不算縮短，因為兩者同時載入
* 將只適用特定路徑的規則搬到該路徑的 nested `CLAUDE.md`，是本 skill 期望的結果，不是規避行數。nested 檔案只在處理該路徑時才載入，確實降低其他工作的 context
* 不為了達到行數限制而犧牲重要的隱性知識
* 不新增模板式前言、結語或摘要段落
* 不擴大到與 Claude 指令維護無關的工作

# 執行順序

0. 先執行 `git status --short`。若審查範圍內的目標檔案有未提交的修改，先列出這些檔案並告知使用者：本次修改會與既有變更混在同一份 diff 中、難以區分。取得確認後再繼續；非 Git repository 時直接說明無法提供 diff 保護。
1. 找出所有相關檔案與 import 關係。
2. 將每條內容拆成原子規則。
3. 使用程式碼、設定、測試及文件確認其正確性。
4. 判斷每條規則的處置類型。
5. 檢查 root、nested rules 與 Skills 之間的重複和衝突。
6. 直接修改相關檔案。
7. 確認搬移後沒有遺失重要限制。
8. 檢查 Markdown 與 YAML frontmatter 格式。
9. 檢視最終 diff，避免修改非目標檔案。

不要只提出建議而不修改檔案。

遇到無法由 repository 證實、但可能是重要隱性知識的規則時，保留精簡版本，並列入「待人工確認」，不得自行刪除。

# 完成標準

全部符合才算完成：

* 每條原始規則都已被審查
* 所有保留規則都有正確作用範圍
* task-specific procedure 不再常駐於根目錄
* 沒有明顯過時、重複或互相矛盾的指令
* 重要不變式、同步修改要求及 source of truth 沒有遺失
* 沒有修改產品程式碼
* 新增的 Skill frontmatter 有效
* 最終 diff 僅包含必要變更

# 最終回報

保持精簡，只輸出：

1. 修改的檔案
2. `保留／搬移／改寫／刪除／新增` 的規則數量
3. 最重要的變更
4. 發現的衝突或過時資訊
5. Enforcement gaps
6. 待人工確認項目
7. 每份 `CLAUDE.md` 修改前後的行數；本次新建的檔案標示為「新建」並只列最終行數

若不需要修改，明確說明已檢查的範圍及沒有修改的原因。
